# Codex V2 聊天契约

Last updated: 2026-10-22
Status: active
Owner: maintainers

## 已确认目标

当前主链路以同一线程在发送、流式显示、刷新重进和桌面更新后保持一致为目标；消息失败后可见且可恢复；长历史按需读取；用户正文与宿主包装分离；文件 diff 和图片不因状态转换丢失。本文记录已落地的接口与行为，发布验收结果另行记录。

本方案取代旧方案中全量 snapshot 广播、单一助手正文槽位、POST+SSE 主链及多套 canonical 往返。Codex 采用官方 Thread / Turn / Item 身份与内容；旧 JSONL 仅在入口适配一次。CC 终端通道独立保留。

## 责任边界

- 官方 Codex 持有完整历史。网页仅维护可重建的有界读取缓存及独立请求回执，不复制永久完整历史。
- `CodexHistoryReader` 读取官方 typed 历史并生成有界的展示条目，完整工具输出和 diff 使用详情接口。
- `CodexThreadService` 负责每线程串行发送、官方事件订阅、请求与官方 turn/item 关联。不得使用 legacy projector/conversation 构造 Codex 主状态。
- `CodexRequestStore` 在应用 dataDir 原子持久化独立请求文件。请求同 ID 同内容返回原回执，同 ID 不同内容拒绝。重启时 dispatching/accepted/running 恢复为 unknown，通过官方历史自动核对，不自动重新派发。
- 前端 Codex store 每线程只有一份 turn/item 数据，另外保存待确认请求、草稿和连接状态；渲染组件复用，展示结果不回写事实。
- WebSocket 只订阅稳定 threadId 的增量；HTTP 提交和历史读取独立。页面关闭不等于中断生成。

身份就绪、正文读取和模型目录各自推进，目录慢或失败不阻塞已确认线程的阅读与发送。线程设置读取和运行时打开仍须完成后才能发送；首次服务器回执列表必须成功读取并应用，失败或结构无效不能当作空列表解锁，成功重试后恢复，未决回执与设置保存屏障继续生效。目录结果只更新模型选项，不覆盖线程已有设置、草稿和附件；目录失败通过现有重试入口恢复。配置按当前 App 认证代次共享，成功有效 60 秒，显式重试可强制刷新，身份失效后所有旧响应停止应用。分组新增线程仅传项目与工作区身份，由服务端采用实时默认设置，不让目录加载时的占位值或旧缓存覆盖默认；已有会话升级及 API 调用方的明确设置仍保留。

模型、思考强度和权限选择是浏览器本地按 threadId 保存的输入设置草稿，运行期间也可修改；选择时不 PATCH 官方线程 SQLite、不更新运行时设置，也不改写已提交消息。存在待应用改动时，下一次手动发送携带 model/reasoningEffort/permissionMode 的完整快照；当前仍在运行则自动排队开启新轮。未改设置时保留原引导/排队方式。自定义权限未被明确重新选择时不补成默认权限，发送仍执行既有权限校验。输入设置里的 Git 分支只读展示当前分支、工作区状态和错误，不提供切换或新建分支操作。

## API 契约

所有端点要求现有认证；写操作保留 Origin 校验。新前缀 `/api/v2/codex`，Codex 对话状态只消费 V2；侧栏、设置、图片上传等辅助功能复用既有接口。

| 方法 | 路径（相对新前缀） | 内容 |
| --- | --- | --- |
| POST | `/threads` | 创建官方空线程，接收 cwd/name/projectId/model/reasoningEffort/permissionMode，返回 `{thread}` |
| GET | `/threads/:id` | `{thread}`，含 id/name/cwd/model/status；仅读取，不恢复执行 |
| GET | `/threads/:id/initial-history` | `{turnsPage,itemsPage}`，最新 1 轮与最新 30 条正文一次返回；空会话 itemsPage 为 null，保留各自向前翻页游标 |
| GET | `/threads/:id/turns?cursor=&limit=10` | `{threadId,turns,olderCursor,hasMore}`，按时间升序提供本页；cursor 用于向更早历史翻页 |
| GET | `/threads/:id/turns/:turnId/items?cursor=&after=&limit=30` | `{threadId,turnId,items,nextCursor,hasMore,latestItemId}`，cursor 优先；after 为最后已加载 item ID，只读取其后的新条目；网页显式请求 30，服务端既有上限不变 |
| GET | `/threads/:id/turns/:turnId/items/:itemId` | `{item}`，完整单条内容；超大字段明确分页或截断标记，不能伪装完整 |
| GET | `/threads/:id/turns/:turnId/items/:itemId/images/:index` | 对应 item 的内嵌图片字节；验证图片类型与 20 MiB 上限，不读取任意路径或抓取远程 URL |
| POST | `/threads/:id/requests` | `{clientRequestId,mode,expectedTurnId?,input:{text,attachments:[{id}]},options:{model,reasoningEffort,permissionMode}}` → `{request}`；mode 为 `queue` 或 `steer`，携带设置时统一按 `queue` 保存，不用引导忽略设置 |
| POST | `/threads/:id/requests/:requestId/steer` | `{expectedTurnId}`，将未携带新设置、尚未派发的本地排队请求转为当前轮引导；复用原请求 ID、正文和附件，重复调用不重复发送；`settingsQueue` 不允许转换 |
| POST | `/threads/:id/requests/:requestId/cancel` | 撤回尚未执行的 `settingsQueue` 或桌面官方队列消息；若已开始派发或执行则返回冲突，不伪装取消成功 |
| GET | `/threads/:id/requests` | `{requests}`，返回该线程有界近期回执，包括未决请求 |
| GET | `/threads/:id/requests/:requestId` | `{request}` |
| POST | `/threads/:id/interrupt` | `{expectedTurnId}`，停止用户当前看到的轮次；网页持有时走 app-server，桌面持有时走 owner 定向中断。返回 `{ok,turnId,goalPauseError?}` |

回执：`{id,threadId,state,mode,expectedTurnId?,input,options,executionRoute?,upstreamQueueId?,turnId?,userItemId?,error?,createdAt,updatedAt}`。
state 为 `received/dispatching/queued/accepted/running/completed/failed/interrupted/rejected/unknown/cancelled/removed`。`queued` 表示请求已保存并等待执行，不等于已开始；`executionRoute=desktopQueue` 为官方输入队列，沿用原桌面线程设置；`settingsQueue` 为网页服务通过请求日志持久化的设置队列，每条保留独立 input/options 快照，等待下一轮。设置队列通过桌面 owner 派发时标记为 `desktopSettings`，由原 owner 接收完整设置并返回 turnId。未派发的设置队列可撤回，重启后继续等待；已经派发而回执不明的消息转为 unknown，只核对而不重发。
202 表示请求已可靠保存，不等于 Codex 已接收。浏览器超时或上游响应丢失应查询原 ID；unknown 不自动重发、不允许后续请求越过未决请求。

当前二进制 schema 支持 `clientUserMessageId`，历史 userMessage 支持 `clientId`。用它建立关联，但不假设官方重复 turn/start 自动去重。

实时 item 的可见身份独立于历史窗口加载状态：启动首次内容读取时保留已显示的实时消息，历史页使用官方位置和分页边界合并排序，HTTP 追上后按同一 item ID 合并。摘要仍不自动进入可见窗口；已加载详情不被更短的有界摘要覆盖，运行状态继续更新，新的摘要正文增长或变化时重新要求详情。

实时内容和发送状态自动更新，无需点击“加载本轮更多内容”或“查询发送状态”。官方 turn summary 当前只返回用户与助手摘要；最近页和新加载的可见历史页自动按页补齐中间消息、文件和过程条目；同一时刻最多两个轮次读取，完整终态旧轮不重复读取。最新轮再使用 `items?after=<itemId>` 读取新增记录；执行过程默认折叠，展开可补读未加载的详情。空增量页保留 latestItemId，不从首页重扫整段历史；断线或状态变化时按需核对末条详情。网页持有的轮次消费 app-server 的 item delta；桌面持有的轮次只能逐项读取已持久化的内容，单条消息内部的 token 增量不在跨运行时只读接口中。

运行中提交的排队消息先放在输入区上方的暂存列表，提交中、等待、失败或接收待确认时保持原位置；确认执行并关联 turnId，或对应官方 user item 到达后，再进入时间线。空闲时直接发送和立即引导仍进入时间线，不因短暂排队来回跳动；刷新重进保留已知初始位置，缺少位置记录的待发送回执按队列展示。官方 user item 到达后按 clientId 或 userItemId 接替，不留下重复项。未携带设置且尚未派发的网页本地排队消息可点“引导”转给当前回复；带新设置的消息必须等下一轮，不能用引导丢弃快照。撤回项从暂存列表移除，未确认投递及失败项保留核对或恢复入口。

API 省略 mode 时默认为 `queue`，页面未改设置时采用当前发送方式配置。网页持有的当前轮运行时，排队消息先保存回执，待其完成后启动新轮；`steer` 使用官方 `turn/steer`，必须携带当前 `expectedTurnId`，目标已结束或不由网页持有时明确拒绝并保留消息。用户修改设置后的手动发送按已确认规则使用 `queue`，当前轮不应用这些新设置。引导消息与原输入可以属于同一 turn，但仍有独立请求和 user item 身份。`interrupt` 按实际执行归属停止指定轮次；网页持有的轮次调用 `turn/interrupt`，可发现桌面 owner 的轮次通过原生 v4 `thread-follower-interrupt-turn` 传入 `expectedTurnId`。页面停止能力独立于引导和提问能力，桌面任务无需网页发送回执即可停止；活动轮次首次未发现桌面 owner 时，按 10 秒最短间隔重读 metadata，恢复连接后重新启用停止，不反复加载整段历史。目标已结束或已换轮返回 null 并刷新真实状态，不中断后继轮；并发重复点击合并，回执不确定只读核对不自动重发。已有旧客户端仅对网页明确持有的轮次兼容省略目标。定向停止作用于当前轮次，不承诺同时暂停持续目标；关闭页面不等于停止。未知回执自动核对，不盲目重发，也不允许后续排队请求越过未决请求。

服务器按原 ID 返回 `receipt_not_found` 后，用户可显式解除发送锁定；解除前必须再次读取并确认 404。解除只保存本地 `confirmationDismissed=true`，原文、回执及 `unknown` 状态继续保留，不代表发送成功或失败。已解除且仍缺失的回执不再驱动定时轮询，也不会随其他活跃轮次的定时同步反复按 ID 查询；重新打开页面、WebSocket 重连或同步、页面回到前台和用户显式刷新/核对时仍查询原 ID。单条回执读取按 ID 去重，已解除与正常请求各有一个串行读取通道，总并发最多两条，页面卸载后未开始的读取不再执行；瞬时网络失败不会撤销这次人工解除或恢复高频请求。已解除回执的慢查询不占用常规轮询或最新页刷新，其他未决请求和活动轮次继续原有退避同步。服务器之后通过列表、单条查询或 WebSocket 返回同 ID 时，清除本地解除标记并以官方状态收敛；官方仍为 `unknown` 时恢复发送锁定及自动核对。所有核对均不自动重发，也不以等待时长把真实 `unknown` 转成终态。

排队区的“引导”同时支持网页持有任务和具备 `desktopQueuedSteer` 能力的桌面任务。桌面队列沿用原请求 ID，后端串行处理同会话的引导和撤回：删除前持久化领取阶段，只有官方队列明确返回 `deleted:true` 才向原生 follower 通道投递。领取或投递不明确时保留 `unknown`，只读核对原 client ID，不自动删除、重发或恢复为 queued；已领取但明确未发送时保留可恢复原文。发送前重查 owner 和活动轮次；接收回执记录原生实际 turn ID，不把网页当成执行 owner。携带新设置的消息继续等待下一轮，不通过引导丢弃设置。

桌面 follower v1 没有原子 expectedTurnId 参数，发送前复查只能缩小换轮窗口，最终以原生回执为准。网页的串行锁不等于桌面原生 MessagePort 队列锁；若同时在桌面点击同条消息引导，仍存在原生已发出但尚未删队列的竞态。当前不承诺跨端同时操作的恰好一次投递。手机操作的连续点击、网页多请求、网络超时和服务重启按持久回执去重，不自动重试不确定投递。

官方 `thread/queue/add` 仅保存输入，不接受模型、思考强度或权限快照；未携带设置的 `desktopQueue` 保持原行为。携带设置的请求由 `CodexSettingsDispatcher` 留在本地持久队列，等已知当前轮结束且原桌面队列为空后，通过 `thread-follower-start-turn` v2 向既有 owner 发送完整设置，关闭桌面设置继承，不抢占 owner 或更新旧队列设置。发送前重新确认 owner，并通过 `beforeSend` 再读最新轮次和官方队列；发现变化就继续等待。原生协议没有原子 idle/start 前置条件，这些复查仅缩小竞态窗口，仍无法完全排除复查之后桌面同时开始新轮；不能宣称已消除此限制。投递后回执不确定时不自动重发或改走 steer。

WebSocket：`/ws/codex?threadId=<id>&epoch=<epoch>&after=<seq>`。外层统一为 `{schemaVersion:2,threadId,epoch,seq,type,payload}`。事件：

- `sync.required`：首次订阅、epoch 变化或缓冲缺口，payload 可包含 thread/current request；客户端补读近期页，保留已加载旧页和未确认消息。
- `item.upsert`：payload `{turnId,item}`。
- `item.delta`：payload `{turnId,itemId,field,text}`；field 为 text/summary/aggregatedOutput。按 itemId 追加，完成 item.upsert 替换完整文本。
- `turn.upsert`：payload `{turn}`；省略 items 不删除已有 items。
- `turn.metadata`：历史观察器发送最近两轮的状态和时间等元信息，不携带 items。客户端仅更新已加载轮次，不插入未知旧轮、不改变轮次顺序、分页或可见窗口；原生 `turn.upsert` 仍可引入新轮次。已读取正文的旧轮进入终态后，以原 tail 的 after 增量及末条详情收尾，详情完成后才标记已完成对账。
- `request.updated`：payload `{request}`。
- `history.changed`：官方外部更新；客户端补读最新页，不能停同步。
- `thread.updated`：payload `{thread}`。

seq 属于网页服务事件流，epoch 标识当前事件缓冲，在服务重启或缓冲重建后改变；不能拿官方历史的 turn 数当版本。分页和同 epoch 事件有竞态时，旧页不得覆盖读取期间收到的更新。收到新 epoch 必须通过订阅握手确认，不能被旧 socket 迟到事件切换。

## 展示与历史契约

首屏仅在当前认证响应明确包含 `capabilities.initialHistory:1` 时使用聚合读取。能力随 session、手动登录和自动续登更新，身份失效时清除；旧后端不提供字段则继续 turns → items。聚合接口 404 时重新核对能力，确认后端已回退才使用旧接口；真实不存在的会话及超时不自动并发重试另一套请求。

聚合读取复用一次请求前的 read 令牌，完整 item 优先于同批摘要，期间到达的 WS 新内容保持优先；HTTP 不改变 epoch/seq。仅初始化使用聚合接口，正常刷新和追新仍用增量路径。进入时显示最新正文，触顶依次补当前轮更早条目和更早轮次；元信息、设置、回执和提问保持各自就绪门禁。

排序依据为官方完整分页的相邻关系及请求锚点。稀疏摘要只能补入未知身份，不能以 upsert 时临时追加的位置作为既定顺序；向前翻页以当前窗口首条作为 before 锚点，优先于摘要中已见 ID 的临时位置。重连或重新核对最新尾页保留已经加载的更早条目，缺项不解释为删除。首屏只显示倒序取得后恢复正序的最新 30 条，追新只读取 tail 之后。

向前翻页时，同轮更早内容每次最多读取 90 项；已有轮次的缺页补齐后，每次再读取最多 3 个更早轮次的摘要及各自最新 30 项，批量内容请求最多并行 2 个。失败时等待同批在途请求结束，重试仅补未成功的轮次；批量中间轮次的更早游标同样保留可达。首屏和实时追新仍为 30 项，不在闲置时连续读取整段历史。触顶与阅读锚点规则不变，跨轮次批量返回按官方时间顺序展示。服务端显式内容页上限为 90，默认仍为 20。

代码高亮仅在 Markdown 代码块出现时动态加载共享模块。加载前先显示同结构的安全转义文本，加载失败保留可读正文；高亮就绪只使相关渲染缓存失效，冷/热输出均保留 DOMPurify。净化和 Markdown 解析仍在正文必需路径，代码块内部滚动位置在内容相同且组件仍挂载时恢复。

- 展示适配与轮次模型缓存按线程 context 隔离，未变的历史 turn/item 保留引用，时间线复用父级模型。顶层详情标记变化仍需重新派生，嵌套正文和 presentation 通过 upsert 替换对象更新；不得原地修改嵌套内容后依赖缓存自行发现。缓存不修改事实状态或上次展示结果，模型选项变化必须失效。
- 初次打开和刷新完成后自动滚到底部；已贴底时跟随新内容及异步布局增长。用户主动上翻后保留阅读位置，只有重新到底部才恢复跟随；自动恢复和程序化滚动不能被误判为主动上翻。
- typed item 原样保留稳定 id/type/phase/状态等语义；可附 `presentation:{text,images,fileChanges}`，由后端一次生成。
- 用户宿主包装仅在识别明确模板和附件证据后提取实际请求；原始官方输入不修改。代码块、引用、普通同名标题不得截断。未知包装保留原文。完整的浏览器环境模板支持 HTTP(S) 与 `file:///` 本地页面地址；仅清理展示文本，不读取地址对应的文件。
- 本地图片使用受认证 URL，内嵌 base64 转为单条媒体接口地址，避免历史 JSON 携带完整图片字节；归一化后去重，绝对本地路径不直接作为 img src。远程图片保留原 URL。
- FileChange 同时适配新版 changes 数组与旧 changes/output/output.changes 路径对象；presentation 保留 diff、previousPath 与完整增删行数，展示状态为 A/D/R/M，原始 kind/type 不被改写。
- 完整 item 页和有序 turn.items 确定官方相对顺序；摘要中的局部序号不代表完整轮次位置，不得覆盖已知顺序。引导回执晚到时使用提交时捕获的 item ID 锚点暂放消息，官方顺序到达后覆盖临时定位。
- 正文按官方 itemId 保留多条，禁止按相同文本合并不同消息，禁止隐藏真实 failed/interrupted 用户消息。
- 历史使用 summary 与有界 item 页，过程预览压缩、详情按需。truncated/truncatedFields/hasDetails 明确内容边界；返回缺少某 item 表示未加载，不表示删除。摘要 position 只表示该摘要内的顺序，分页仍以官方 item 顺序归并。
- 执行过程展开后自动读取需要补齐的条目详情；不为每条过程项提供手动“加载详情”按钮。官方未提供正文的思考项不显示空卡片。完整详情显式清除旧预览截断标记，真实超限仅显示简短部分内容提示。
- 工具过程默认展示紧凑摘要（读取文件、运行命令、调用工具等），各分组按稳定 item 身份独立展开；详情放在无嵌套卡片的时间线中。历史补全不会把展开状态移到另一分组，读取失败在展开区域可见。
- 原生 `subAgentActivity` 独立展示，`presentation.activity` 保留子线程、活动身份、状态、起止时间和耗时。计时取官方分页 entry 的 `startedAtMs/completedAtMs`，按子智能体每次活动的开始/结束配对，不能使用创建调用的耗时。连续分页的有界派生索引保留已知时间，摘要不能跨缺口猜配；必要时用官方 rollout 的有界尾部补充。未知时间保持空值，缺乏运行证据的旧开始记录显示状态待确认。
- 子智能体运行时在前端本地更新计时，完成事件先合并到对应开始活动再去重，完成或组件卸载后停止计时。缺少开始记录的完成活动仍可显示；同一子智能体多次启动分别保留，原始官方事件不改写。
- 子任务状态投影只在同轮已存条目中按明确 `startedItemId` 关联开始和完成，包含当前可见窗口之外的已存证据；不得按子线程名或路径猜配不同唤醒。完成先于开始到达也可收敛，同一开始项的陈旧 running/unknown 摘要不能覆盖已知终态及结束时间。
- 实时投影仅对活动线程和活动 item 有界缓存；收到终态后对账官方数据，旧事件不得覆盖完成内容，官方完整详情可以补齐。

## 执行归属

外部桌面执行的历史摘要可能在 `notLoaded` 时返回缺少 `completedAt` 的 `interrupted`，不能据此认定真实中断。历史页和列表共用只读状态观察：仅从官方 metadata 指定、位于已配置会话目录中的 rollout 读取有界尾部，按 turn ID 核对明确完成/中断记录与最近活动。证据不足时为 `unknown`，页面显示“状态待确认”；WebSocket 不可用时仍退避通过 HTTP 核对最新轮次，确认终态后停止。真正终态不会被旧快照恢复成运行中。

同一官方线程只能由一个运行时直接写入。网页不抢占桌面 owner；官方明确返回 writer 冲突或桌面轮次仍活跃时，未携带新设置的请求通过官方 `thread/queue/add` 持久排队，携带设置的请求按前述 `settingsQueue` 路径等待并由原 owner 开启新轮。官方队列回执保存 upstreamQueueId，两条路径的 `clientUserMessageId` 均沿用网页请求 ID，历史 userMessage 的 `clientId` 用于确认执行；接收不确定时只核对原请求，不重复入队或 start。桌面线程未加载、处于中断状态或持续目标循环时，消息可能等待原端恢复或进入可执行状态，不得显示为已执行。普通查看只读历史，不调用 resume；网页自己持有的线程仍直接使用 resume/start。旧的 `rejected` 回执不自动重发，需用户显式恢复原文后再次提交。

桌面 owner 的实时通知不转发给网页的另一个 app-server。关联到桌面 turn 后，网页按有界间隔只读新增官方 item，及时显示已持久化的说明消息和执行过程；无完成时间的跨进程 `interrupted` 投影不能据此终结请求。单条 agentMessage 在桌面完成该 item 前没有可读取的 token delta，不用完成后的打字动画伪装流式。真正逐 token 同步需共用 owner 事件连接或等待官方只读订阅能力。

旧 CC 的 session/PTY/WebSocket 通道保留兼容；Codex V2 页面不再用旧 POST+SSE、canonical/projector 或完整 snapshot 广播作为主状态。

## 输入与导航连续性

第六轮合成真实控制器与组件检查发现：旧 context 的图片上传完成后可能持久化旧草稿，覆盖往返会话后的新文本；首次设置读取失败后重试未建立设置基线，未更改的桌面设置也被作为 overrides 发出。修复由 CodexThreadView 的同一 owner 完成，所有异步结算绑定原 context 生命周期，首次成功的设置读取建立与正常初始化相同的基线，保留后续用户主动更改和发送保存屏障。

同一调查还复现旧发送 POST 的迟到回执会通过旧 store 持久化整个草稿。现有实现仅合并该回执到当前持久化记录，保留最新草稿与其他新请求，避免旧 owner 的完整快照回写；已发 mutation 继续结算。成功、明确拒绝和未知结果均已覆盖，已有终态与更新时间保护保持；重复 dispose 不重新持久化旧稿。

设置读取的布尔成功兼容值不能被当作当前快照已经应用。共享设置控制器通过 `readComposerStateForThread` 向 V2 提供 applied/preserved/stale/failed 和有归属的服务器快照，旧布尔接口继续兼容。首次基线来自有效服务器快照，期间成功的用户修改不被吸收。重叠重试按最新代次提交错误、基线和解锁状态，较旧成功不清较新失败，保存失败屏障继续独立生效。

HTTP 5xx 和 408 不能证明原消息未被接收，发送结算先保留 unknown 并按原 clientRequestId 核对回执，不产生新的提交。确定的其他 4xx 继续表示拒绝；已知服务端回执及终态以原身份恢复，不能让误标的 rejected 阻止后续核对。

本地乐观发送及传输失败的时间属于客户端时钟，不能用来拒绝服务端确认。回执合并需显式区分本地状态和服务端事实；相同服务端来源内继续按更新时间和终态防止迟到回退，已确认服务端执行也不能被本地网络错误降级。时钟偏差、刷新后unknown与迟到确认同时纳入验证。

按 ID 补查失败同样不是服务端执行状态：已知 received/dispatching/queued/accepted/running 保留已确认事实，继续核对；尚未确认的本地记录或原本 unknown 可记录读取失败。只有原本未知且再次确认缺失的回执才进入既有显式解除发送锁定流程，不能把已确认执行因单次 404 变成可重复提交。

原实现每次 setDraft 都推进通用 revision，导致展示 computed 重新遍历历史；5000 个已加载 items 的合成输入可消耗约 30ms。现保留对账原 revision，并以 `presentationRevision` 分离展示失效，纯草稿不触发历史投影；历史、请求、排序、详情和状态变化继续刷新，不建立另一份事实状态或跳过流式内容。同负载中该段同步成本约 29.536ms 降至 0.006ms，不代表浏览器端到端输入延迟。

列表展开与分页状态由当前认证生命周期的 App 持有，通过单个视图状态对象交给 SessionListView；返回保留分组展开、显示更多和搜索分页，不把这些临时状态持久化到 localStorage。身份变化时清除，保留现有查询和视图模式语义。

只读 GET 生命周期已提取为 `codex-read-requests`，由 chat runtime 负责创建和关闭。切换/卸载 abort 自身未完成的 GET 并清理跟踪；提交、排队、引导、停止等 mutation 不跟随读取取消，不能因切换重发或推测结果。

## 历史分页与传输优化方案

第七轮真实 runtime/route/reader 的隔离链路基准使用10轮、每轮500个完整typed items。现有默认10条触发500次items GET；显式请求现有上限30条降至170次，双reader和完整身份/顺序保持。每个HTTP响应增加50ms的三轮中位补齐耗时约14.066秒降至5.022秒，JSON总正文仅少0.86%，主要收益来自请求数量；不是物理手机或公网性能数据。不增加服务器页上限，不引入batch端点或只保留主消息的过滤。

实施前先将前端loadItems及其进行中Map从chat runtime提取到单一职责的 `codex-history-items`，复用原store、call、disposed判定和详情通知，不迁移轮次队列、详情、socket或mutation。原行为回归后，再由该模块用URLSearchParams统一cursor/after/首请求的limit=30，保持cursor优先、排队并发2、独占anchor、yield和迟到保护；现有测试对URL的断言改为结构化字段验证，原身份/顺序/数量断言保留。

传输基准显示真实呈现形状的27KB混合页以gzip level1降至约4KB、CPU中位约0.17ms；2.87MB中文页降至约379KB，压缩wall中位约6.07ms。新增 `runtime/http/readJsonTransfer` 仅处理V2成功GET的JSON，复用现有JSON序列化和安全头，8KiB以下默认原文，gzip仅在协商允许时使用。保留no-store、鉴权先行和原JSON内容，不建立私有历史ETag/内容缓存，不改变图片、错误或mutation响应。

压缩采用Node现成zlib与流机制约束输出缓冲，覆盖合法大正文，不因超过4MiB而统一放弃压缩。每个runtime至多两个活动压缩，不积累等待正文；满额且允许identity时返回完整原文，identity禁止时明确返回可重试错误。客户端取消及流失败必须销毁整条管线并释放容量，不能把截断内容当成功JSON或在已发送gzip头后回退原文。编码协商、大小字节、断开/失败清理和并发容量须以实际HTTP验证。

已终态item因父turn完成而重复读详情的机会暂不实施，保留既有最终对账语义。退出条件为分页完整性/相同负载对比、传输解码及清理、独立复核、完整门禁和正式浏览器读取验收；真实手机公网与浏览器性能指标另行验证。

上述两个模块已实施。原分页逻辑先等价提取，130 项原行为测试通过后再统一 limit；新增真实 HTTP 用例验证 5000 条 typed items 的完整身份、顺序、正文、重复同文和增量锚点，以及失败续读、cursor 循环和取消。只读独立复核通过；传输另以 16 MiB 正文验证反压、逐字节解压、双槽和断开恢复。

最终流实现的 30 次同负载 loopback 复测：27126 B 混合页压至 4077 B，完整 HTTP p50 增量约 0.196 ms；2871405 B 中文页压至 378952 B，增量约 5.830 ms。这是完整流链路成本，与前述 scout 的独立压缩区间口径不同，不混作 CPU 对照。

本轮全量 1140 项项目测试、10 项预览测试及 check/生产构建通过。实际前端在隔离 Koa/reader 合成环境补齐全部 5000 条，以 170 次 limit=30 items 请求完成；200 条用户消息、200 条 commentary、200 条 plan、10 个最终尾标记可见，加载期间草稿保留，1280px/390px 无横向溢出或控制台错误。正式服务通过管家重载，独立测试会话的历史三端点身份/no-store/解压等价和浏览器读取通过，本轮没有模型发送。慢接收端主动断开仍可能产生非阻断 EPIPE 日志，管线与容量可回收；真实手机公网及 LCP/INP 未测，不能把合成延迟结果作为该目标已完成的证据。

## 当前路由资源预取方案

第八轮核对发现，App 的身份 bootstrap 完成后才挂载异步视图，聊天视图完成下载和挂载后才开始正文读取。隔离实际浏览器的初步时间线在身份延迟 800ms、聊天资源延迟 250ms 时，身份响应约 0.87 秒结束，视图下载此后开始，正文首次请求约 1.16 秒。该数字只证明受控串行依赖，不代表公网首屏指标；正式 A/B 必须使用同一完整 fixture、不同 origin 的冷模块加载并记录服务器时间线。

计划在既有 `async-view` 边界统一预取与实际组件消费的 loader，App 仅选择当前路由对应的静态视图，在身份请求期间开始下载；不抢读线程、配置或目录数据，不改变身份确认和发送屏障。预取不挂载视图、修改 App 状态或触发 reload，进行中读取与随后挂载合并。路由或身份切换后，旧预取只能留下静态模块结果，不能发布数据或触发恢复动作。

显式 Codex 历史预取 CodexThreadView，其他聊天预取两条现有有效路径均依赖的 ChatView；未知 live ID 的 provider 识别仍留在原认证后流程，共用渲染依赖可以先加载。列表和登录各自只预取对应视图，初始路由未解析时不猜测目标。该选择来自当前依赖图，不增加查目录或 metadata 的预取。

Vite 的样式预加载失败会保留内部 seen 标记，清空 Promise 再 import 可能跳过失败样式。因此失败必须保留给实际消费者处理，不能把下一次模块导入成功当作完整恢复；真正消费时沿用有时限的单次旧资源 reload 防护，并覆盖 CSS 失败。后台预取和失效视图不能触发 reload。若实际消费仍失败，应保持可观察错误，不伪装视图已就绪。普通视图错误不能被当作旧 chunk 循环重载。

独立 review 与实际浏览器进一步证实，仅按视图缓存失败不足以保护共用 CSS：ChatView 样式失败后，独立 CodexThreadView loader 仍可能因 Vite seen 跳过该样式，成功挂载未样式页面。修复须让 Codex 视图显式依赖同一份 ChatView 加载结果，共用依赖先注册、模块导入继续并发；消费必须等依赖完整成功，失败沿当前消费者恢复。依赖属于静态组件图，不建立另一份 CSS 文件名解析或复制 Vite 内部状态；无关列表/登录不受聊天依赖失败阻塞。需覆盖依赖仍 pending、已失败、反向进入和离开到无关视图。

退出条件：共享/并发 loader、同步/异步失败、CSS失败、消费与路由/身份隔离、现有 bootstrap/目录/聊天门禁回归，独立 review；受控实际 IAB 冷开 A/B 证实资源请求提前且数据仍在鉴权后，最后完整测试/构建、管家部署、正式只读与窄屏验收。先按边界实现，不扩大到聊天正文渲染器或全路由无差别预取。

该方案已完成。初版独立复核发现的跨视图共用 CSS 缺口已通过显式依赖修复，真实 Vite/Vue 负例先红后绿，复审 57 项与四个独立场景通过；实现相关 239 项及最终全量 1179 项项目测试、10 项预览测试、check/生产构建通过。原 mounted harness 仅补公开 preload 接口；新增 fragment 测试宿主补真实 sibling/anchor 语义，未弱化身份、输入或晚到保护断言。

最终实际 IAB 三个冷 origin 样本在相同合成内容、auth 人为 800ms 和聊天 JS/CSS 人为 250ms 条件下，正文首次请求中位数由 1167.7ms 降至 887.8ms（约 24%）；路由资源在 auth 响应前开始，所有样本业务数据均在身份响应后读取。该值是服务端单调时钟请求时间线，不能作为 FCP/LCP/INP 或物理手机、公网收益。首次入口 JS 比原构建增加约 1.1KB，主体仍按路由分包。

实际浏览器复验共用 CSS 503 后切换视图：当前消费者受限重载后恢复样式，桌面输入框从缺样式时 176px 恢复到 794px；离开聊天到列表后，旧 CSS 失败没有重载或聊天 API。永久样式故障只自动恢复一次，保留可见失败与手动命令；JS 一次失败也可恢复。1280px/390px 正常阅读和输入无溢出，正式服务重载后的独立 QA 只读验收通过；没有新增模型输入或改变权限。真实手机公网指标和慢连接 EPIPE 日志残留继续单独记录，整体持续目标仍未据本轮局部通过判定完成。

## 流式渲染与列表返回方案

第九轮实际 Vue/typed store/presenter/view-model 编译探针发现，同一活动 turn 的对象更新会让正文未变的兄弟项重复 Markdown；24 个 delta、12 条已完成 commentary 的负载中，独立正文字符串 computed 将 Markdown/highlight 从 312 次降到 24 次，所测 CPU 段中位约 209.8ms 降到 46.7ms。三个已有 fence 后追加正文时，组件内按完整源码和语言缓存可令重复 highlight/auto 从 72 次降到 0，约 220.8ms 降到 9.9ms；持续增长的 fence 没有同类收益。这些排除了真实 DOMPurify、DOM、布局与输入排队，不是 INP 或整页加速比例。

实施先等价提取 892 行 ThreadItemRenderer 内 Markdown/code-fence 创建、语言高亮与图片/链接配置到单职责 `thread-item-markdown` 工厂，单组件持有实例；保留组件内实际 DOMPurify 调用、原配置、光箱和事件位置。提取回归后，再使用独立字符串 computed 和有条目数/字符预算上限的 fence 缓存。缓存 key 覆盖完整源码及语言，不缓存失败或跨实例结果；改变源码/语言必须重算，超预算只放弃缓存，不裁剪/降级正文。完成时仍接受权威 item 替换，cwd 变化更新链接；Markdown、图片、链接与清洗安全语义不变，不重写 store 或协议。卸载释放缓存，不积累无限流式版本。

同轮实际 IAB 长列表证实：分组列表在 scrollTop5926.5px 打开第100条后返回0px；最近活动已展开40条、2165.5px 打开第38条后同样返回0px，原展开/分页仍在。列表共用 document 页面滚动，聊天使用内部 message-stream。计划复用 App 认证生命周期内的 list view state 保存有限的 mode/query 与位置/稳定行锚点，独立 `session-list-position` helper 负责捕获/一次性恢复；SessionListView 挂载边界装配，App 只传既有即时 route/auth generation 校验。保持原页面滚动与 preview 布局，不引入 KeepAlive 或持久查询/正文缓存。

列表仍挂载时捕获，返回且内容提交后一次性恢复，优先稳定 session/group 身份与相对视口偏移，缺项回退到有效页面范围。查询或模式不匹配不套用旧快照；轮询和预览开关不反复抢滚动。卸载、身份/路由代次变化或用户主动操作后，旧恢复不能作用于新页面。需要覆盖延迟数据、缩短列表、即时切走/身份清理、旧状态对象隔离、两模式往返及搜索语义，实际 IAB 验证像素位置。

两条源范围独立实施，先冻结再独立复核。浏览器候选构建使用临时 outDir 与独立数据/认证 fixture，确认后才运行默认完整门禁、管家重载与正式只读验收；Vite 当前压缩插件按 options.dir 写入，允许隔离候选产物，不将未验证候选默认写入正式 dist。完成条件包括真实流式 DOM/清洗/图片与文本校准、列表位置及清理，不能以 Node identity sanitizer 探针代替浏览器安全或渲染通过。

## 读取恢复与分页调度方案

第十轮真实模块与编译组件复现：首次 turns 读取连续两次503后，即使服务恢复，稳定回执轮询仍不重读历史，却清空通用错误并隐藏重试入口。另一个已核对404且手动解除锁定的本地 unknown，会让已启用的排队“引导”按钮在 runtime 静默返回；服务器若重新出现该回执，现有合并会清除本地解除标记，必须继续保持真正未知回执的门禁。两项修复均需保留草稿、原请求身份、唯一提交和设置保存屏障。

先将约540行 `codex-chat-runtime` 的 metadata、最新turns、回执列表和进行中合并刷新等价提取到单职责 `codex-read-refresh`，调用仍经过同一 `codex-read-requests`、store和即时disposed检查。提取回归后，为 metadata/turns 失败分别保存归属与恢复需求，只有相应成功才能清错；沿用原轮询退避安排恢复，稳定回执或其他成功动作不能抹掉历史失败。UI沿现有状态与重试入口显示独立历史读取错误，通用动作错误保持原归属，不建立另一份历史事实或在读取失败时猜测空会话。引导仅忽略已确认缺失且人工解锁的本地记录，未解锁和重新出现的未知回执继续阻止；不修改服务端未知策略、不自动重发。

真实 runtime/route/reader/假WS的6轮 `[1,1,1,1,600,600]` 条目、limit30、每页25ms探针中，两条长轮占满双槽，用户展开旧轮的首个items请求约等待663ms；三个客户端约716ms。计划在前述读取刷新产物冻结后，串行提取 item hydration、可见/展开归属和双槽等待调度到单职责 `codex-item-hydration`，原公开 runtime 接口与详情读取职责保持。先等价验证，再将整轮占槽改为每页释放，用户显式展开的待页可提前到下一空槽；其余轮次仍须公平穿插且最终完整补齐，不能因永久最高优先级饥饿，也不能突破双槽、预读无限页或裁剪正文。完整cursor/after、权威重写、终态对账、错误恢复、进行中合并、卸载和等候者清理须保持。

渲染独立包仅让 process code 的语言成为独立primitive computed，避免未变的已完成命令因兄弟item更新重复高亮/清洗。4条各43749字符命令与24次answer增量的真实typed/Vue探针中，独立语言计算可让重复高亮96降至0；该结果排除真实DOMPurify/DOM/布局，仍需实际渲染与安全核对。保持r9的缓存预算、清洗配置、cwd和内容语义，不通过增加缓存容量掩盖重复失效。
